# Issue 013 — Unbounded retry loop for permanently failing files

## Problem

`pipeline-hpc-submit.sh` builds each cycle's work list by re-globbing `sync/input/` at submit time, writing the result to `logs/pipeline-manifest-<ts>.txt`. Because files are never removed from `sync/input/` automatically, any file that consistently fails processing (e.g. corrupt audio, unsupported codec, missing language model) will be included in every subsequent manifest and resubmitted indefinitely.

## Impact

- Wasted GPU allocation on known-bad files every 10-minute polling cycle.
- No signal to operators that a file has failed repeatedly — it silently re-enters the queue.
- Log volume grows unboundedly as the same failure is recorded across cycles.

## Root Mechanism

The design is intentional for idempotency (surviving transient failures), but there is currently no upper-bound on retries and no quarantine path for files that have exceeded a failure threshold.

## Proposed Resolution

One of:

1. **Quarantine on N failures** — after a configurable number of consecutive failures, move the file to `sync/failed/` so it is excluded from future globs.
2. **Failure manifest** — maintain a `logs/pipeline-failed.txt` blacklist; filter it out during the glob step in `pipeline-hpc-submit.sh`.
3. **Operator alert** — emit a structured warning when a file appears in more than N consecutive manifests without producing output.

## Status

Open. The README Manifest files section documents this behaviour as a known implication of the re-glob design.
